# הקמה והפעלה

המסמך מתאר הכנות למימוש. לא הוקמו שירותים ולא נוצרו סודות במסגרת חבילת המסירה.

## 1. מה צריך מהחברה

- אדם עם גישה להגדרת Google OAuth של הארגון.
- בחירת כתובת אתר קבועה וספק אירוח שמריץ את שכבת השרת.
- מסד PostgreSQL. ההמלצה היא להשתמש בתשתית קיימת מתאימה; Supabase הוא חלופה מוצעת.
- אחסון פרטי לתמונות שער, נדרש בגרסת ההגשות.
- גישה של yuval.b@zemingo.com לבדיקה כמארגן.
- חשבון עובד נוסף לבדיקת הרשאות רגילות וחשבון חיצוני לבדיקת חסימה.
- שעות המוקדמות ב־26.10 ושעת ההצבעה בגמר ב־29.10 — נדרשות לפני הפעלת ההצבעה.

אין לשלוח סיסמאות או מפתחות בצ׳אט. מכניסים אותם למשתני הסביבה המקומיים או להגדרות הסודות של ספק האירוח.

## 2. Google OAuth

בהתאם לספריית האימות שנבחרה ולתיעוד העדכני:

1. הגדר אפליקציית OAuth מסוג Web בפרויקט שבשליטת החברה.
2. הגדר את קהל האפליקציה בהתאם למדיניות Google Workspace של החברה.
3. קבע את כתובות ההחזרה המדויקות של סביבת פיתוח ושל האתר הקבוע.
4. עבור הנתיב המקובל של Auth.js:
   - מקומי: http://localhost:3000/api/auth/callback/google
   - הפעלה: https://YOUR_APP_HOST/api/auth/callback/google
5. אם הגדרות הספרייה/נתיבי האתר שונות, Claude חייב להציג את הנתיב בפועל לעדכון ההרשאה; אין לנחש כתובת.
6. הוסף את Client ID ואת Client Secret רק במיקום המיועד לסודות.
7. ודא שהאפליקציה מבקשת רק פרטי זהות בסיסיים.
8. בדוק כניסה של עובד אמיתי וחסימה של חשבון מחוץ לארגון.

הגבלת קהל ב־Google אינה מחליפה את בדיקת hd=zemingo.com בשרת. הרשאת המארגן קשורה לזהות מאומתת של yuval.b@zemingo.com.

## 3. מסד נתונים

- צור סביבות נפרדות לפיתוח/בדיקות ולהפעלה.
- העתק את חיבורי מסד הנתונים מהספק; אין להרכיב hostname משוער.
- בשרת ללא מצב קבוע, התאם את חיבורי ה־pool, ה־SSL וה־prepared statements להוראות הספק וה־driver.
- השתמש ב־DATABASE_URL להרצת האפליקציה וב־DIRECT_URL לחיבור המתאים למיגרציות, אם התשתית דורשת הפרדה.
- הגדר תפקיד אפליקציה מוגבל ותהליך מיגרציות נפרד בהתאם ליכולות התשתית.
- אל תחשוף טבלאות הרשמות, פתקים או משתמשים ל־Data API ציבורי.
- הפעל migrations מבוקרות ו־seed idempotent להגדרות התחרות; לא לנתוני עובדים או לקולות אמת.
- לפני שינוי סכימה בסביבה עם נתונים, הכין גיבוי ודרך שחזור.
- אין להריץ reset/drop של מסד אמיתי כדי לפתור בעיית מיגרציה.

## 4. תמונות

- Bucket פרטי לתמונות שער.
- הרשאות קריאה שונות לטיוטה ולתוצר שפורסם.
- מפתח אחסון בעל הרשאה גבוהה נשאר בשרת בלבד.
- אין להשתמש בכתובת ציבורית קבועה כדי לעקוף בעיית הרשאות.
- העלאה מוגבלת לסוגי תמונה ולגודל שהוחלט.
- גישה לאחר פרסום עדיין דורשת כניסה ארגונית במערכת; קישור חתום תקף לזמן מוגבל הוא קישור שניתן להעביר בזמן תוקפו.

## 5. משתני סביבה

הקובץ .env.example מציע שמות מפורשים ללא סודות. Claude ימפה אותם בפועל להגדרות הספרייה שבחר; השמות אינם הבטחה לזיהוי אוטומטי בכל גרסה.

- משתנים ציבוריים אינם מכילים סודות, מפתחות שרת או כתובת מסד עם סיסמה.
- קובצי סודות לא נכללים ב־git.
- משתני Google והמסד נדרשים לחיבור אמיתי בגרסה 1.
- משתני התמונות נדרשים כשמוסיפים אחסון בגרסה 2.
- יש לייצר סוד סשן אקראי ולשמור אותו בתשתית.
- תאריכים וכללי תחרות נשמרים כמקור אמת אחד בצד השרת/מסד; אין להעתיק אותם למספר משתני לקוח.
- אין להגדיר מזהה משתמש עוקף, מפתח OpenAI או מצב fake auth להפעלה אמיתית.

## 6. לפני פתיחת הרשמה

- הדדליין ושעת הסגירה מאושרים ומוצגים לפי שעון ישראל.
- כניסה אמיתית פועלת בשני חשבונות ארגוניים.
- חשבון מחוץ לארגון נדחה.
- yuval.b@zemingo.com יכול לנהל; עובד רגיל אינו יכול.
- הרשמה נשמרת לאחר יציאה וחזרה, ואינה מוכפלת בלחיצות חוזרות.
- טופס ההצטרפות דורש שם מלא, Studio/R&D/Strategy ואווטר; שלושתם נשמרים יחד עם ההרשמה.
- משתמש שמתחבר בלבד או בוחר רק לצפות ולהצביע אינו מגדיל את מספר הנרשמים.
- כל דמויות הקטלוג נטענות במחשב ובנייד, ונבחרות גם במקלדת.
- כללי התחרות העיקריים מוצגים לעובדים.
- ברור למארגן מהו מספר הנרשמים ומהו מספר ההגשות.
- גרסת האתר ותוצאות הבדיקה תועדו.
- כתובת האתר אכן זמינה ומחוברת למסד ההפעלה.

## 7. לפני כל הצבעה

- רשימת התוצרים והגרסאות הזכאיות נעולה.
- נקבעו זמני פתיחה וסגירה; המארגן בדק אותם.
- מספר בחירות, הצבעה עצמית, החלפת פתק וחשיפת תוצאות סגורים.
- בדיקת שמירה ורענון בנייד עברה.
- בדיקת מקביליות וסגירת סבב עברה במסד אמיתי לבדיקה.
- מנגנון תיקו ופרסום נבדק.
- קיימת דרך ליצור גיבוי ולסגור סבב ללא שינוי קולות.

## 8. בזמן האירוע

1. ודא שכל הפיינליסטים הוצגו לפני פתיחת ההצבעה, לפי ההצעה הנוכחית.
2. פתח סבב והצג לעובדים את הקישור או קוד ה־QR.
3. עקוב אחר מספר מצביעים, לפי מדיניות החשיפה שאושרה.
4. סגור הצבעה. המתן לאישור סגירת השרת, לא רק לשינוי כפתור.
5. בדוק תוצאות; הכרֵע תיקו אם נדרש ותעד את ההחלטה.
6. פרסם את הזוכה.
7. השאר תוצאות לקריאה בלבד.

אין להמציא בזמן האירוע כלל חדש למקרה חריג. במקרה תקלה יש לעצור את השלב, לשמור את הנתונים ולפעול לפי החלטת המארגנים המתועדת.

## במימוש בריפו הזה

- Redirect URI ל־Google: `<APP_ORIGIN>/api/auth/callback/google`.
- מיגרציות: `DIRECT_URL=... npm run db:migrate` (או `DATABASE_AUTO_MIGRATE=true` בחיבור הראשון).
- אין לייבא נתוני פיתוח: `.data/` (PGlite) ו־`npm run dev:seed` הם מקומיים בלבד.
- בדיקת עשן אחרי פריסה: כניסה עם חשבון @zemingo.com → עמוד הצטרפות; Gmail פרטי → "החשבון אינו מורשה"; עובד רגיל ב־`/admin` → "אין הרשאה"; yuval.b@zemingo.com רואה "ניהול"; בדשבורד מוצג "סגירת הרשמה: סוף יום ד׳ 14.10.2026".
- פירוט מלא של משתני הסביבה והסטיות: [IMPLEMENTATION_LOG.md](IMPLEMENTATION_LOG.md).

## פריסה ל־Vercel (מימוש בריפו הזה)

1. Vercel → Add New → Project → Import את `Boaz35/halloween2026`. Framework: Next.js; שאר ההגדרות כברירת מחדל. ה־Production Branch הוא `main`.
2. Environment Variables (Production):
   - `DATABASE_URL`: מחרוזת **Transaction pooler** של Supabase (פורט 6543) עם הסיסמה.
   - `AUTH_SECRET`: מחרוזת אקראית (`openssl rand -base64 33`).
   - `APP_ORIGIN`: `https://<project>.vercel.app` (או הדומיין הקבוע).
   - `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`: מ־Google Cloud. בלעדיהם האתר עולה, אבל אי אפשר להתחבר.
   - **לא** להגדיר `DEV_LOGIN_ENABLED` או `DEV_FAKE_NOW`.
3. Deploy. אזור הפונקציות נקבע ל־`syd1` ב־`vercel.json`, ליד מסד הנתונים.
4. ב־Google Cloud → Credentials → OAuth client: להוסיף Authorized redirect URI `https://<domain>/api/auth/callback/google`.
5. מיגרציות עתידיות: `npx tsx --env-file=.env.local scripts/migrate.ts` (משתמש ב־`DIRECT_URL`). Vercel לא מריץ מיגרציות בפריסה.
